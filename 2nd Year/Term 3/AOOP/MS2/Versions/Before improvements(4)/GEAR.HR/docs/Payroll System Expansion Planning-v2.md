Domain stays free of storage code.<br>- **Trade-offs:** More SQL boilerplate; strong fit with existing repository interfaces and course JDBC path; we control multi-table finalize in `PayrollProcessor`.<br><br>**Design discussion — ORM-oriented (conceptual)**<br>- **Responsibility:** Entity manager / mapper layer often merges with domain (annotations on `Employee`, etc.) or hides behind generic repositories.<br>- **Visibility:** Persistence behavior less visible; lazy loading and cascade rules affect design reviews.<br>- **Trade-offs:** Faster simple CRUD; harder to model `PayrollData` as map-keyed value object, HM3 append-only audit, and bulk snapshot insert without careful mapping; adds framework learning beyond course JDBC focus.<br><br>**Comparison for GEAR.HR:** JDBC preserves the CSV-era **interface + swap** habit and keeps payroll finalize auditable. ORM would likely require refactoring domain types and obscuring batch/finalize transactions—acceptable in greenfield apps, but a poor match for our current layered CRC and repository contracts.
